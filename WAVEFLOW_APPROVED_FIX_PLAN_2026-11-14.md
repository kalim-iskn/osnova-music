## 1. Типы релизов Muzofond — согласовано

### Что доказано

Приложенный HTML CORTISOL содержит `collectionTopLabel` со значением `Сингл`. Локальный вызов текущего парсера возвращает:

```text
release_type = single
complete = true
tracks = 1
track audio ID = 9694699
duration = 151
```

В БД альбом `31 / cortisol` существует, `genius_id = null`, оба поля типа пустые. Трек `14` связан с Genius-песней `12455562`.

Причина находится ПОСЛЕ HTML-парсера:

- `attachMatchedSourceSingles()` создаёт релизы в конце обработки через `upsertAlbumFallback()`.
- `localAlbumsForArtist()` кеширует список локальных альбомов в памяти сервиса.
- `upsertAlbumFallback()` не вызывает `rememberLocalAlbum()` и не инвалидирует этот список.
- `saveMuzofondAlbumTypes()` ищет альбом в старом списке и не видит только что созданные релизы.

Проверка БД: 201 релиз без Genius ID альбома, но с хотя бы одной сопоставленной Genius-песней; у всех 201 `muzofond_album_type IS NULL`. Это не число всех альбомов без типа и не утверждение, что у каждого из остальных альбомов тип обязан быть известен.

### Что согласовано сделать

- Сохранять известный тип непосредственно при создании/обновлении соответствующего релиза, не полагаться только на поздний проход.
- Обновлять/инвалидировать локальный список после создания fallback-альбома.
- Проверить обычный проход, fallback, создание source-single и возобновление после checkpoint.
- Приоритет итогового типа: известный Genius `album_type`, иначе известный Muzofond `release_type`, иначе null.
- Пока оставить два исходных поля `genius_album_type`/`muzofond_album_type`. Пользователю объяснено: они хранят сведения двух источников, на фронт идёт один итоговый тип. Удаление полей/миграция ради этой ошибки не нужны и не согласованы.

### Проверки

CORTISOL на реальном HTML; несколько синглов создаются ПОСЛЕ заполнения кеша альбомов; Genius типа нет; Genius тип есть и имеет приоритет; повторный запуск не стирает известный тип пустым значением и не создаёт релиз повторно.

## 5. Полные дубли и несовпадающие правила сравнения — согласовано с особой осторожностью

### Общая проверка БД

- 38 групп с одинаковым ненулевым Genius ID и одинаковой длительностью, включая группы с разными основными артистами.

### Подтверждённые механизмы

1. `findExistingOccurrenceOwner()` ищет внутри одного `artist_id`; `reconcileDuplicateGeniusSources()` тоже ограничен основным артистом текущего прохода.
2. `canConsolidateMatchedSource()` требует равенства `duplicateSourceTitleKey()`, хотя Genius-матчинг уже признал два написания одной песней.
3. Разные исходные названия альбомов запрещают объединение даже когда различие — написание одного релиза. При этом действительно разные издания защищать необходимо.
4. SQL-предварительный отбор для источников без Genius ID в некоторых ветках требует буквального `LOWER(muzofond_album_title)` до более умного сравнения. Подходящий кандидат может не попасть на последующую проверку.
5. Финальный проход не обрабатывает все песни, затронутые парсингом, если основной артист трека оказался соисполнителем.
